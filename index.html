      How I work

      The part that matters after launch day.

      Built as a suite, not a pile

      These eleven are part of a nineteen-plugin system. Nothing reaches into another plugin's classes — everything goes through one shared core that owns the database pool, the economy abstraction, the command router and the service registry. Adding the twentieth plugin costs the same as adding the second.

      Measured, not guessed

      Performance work starts with a profile, not a list of settings copied off a forum post. I find what is actually costing your server its tick budget, change that, and measure again — on a running server, without the downtime a rebuild would cost you.

      Optional dependencies stay optional

      Every external hook degrades instead of failing. No Model Engine? Emotes fall back rather than erroring on every use. No BetterHud? Notifications drop to the next renderer. Your server does not go down because a dependency did.

      Versioned and shipped deliberately

      Every fix bumps that plugin's version, in the same commit, with a note saying what the number contains. CI builds the jars; a deploy is verified against the server afterwards, not assumed. You can always tell which build you are running.

      Documented for the next developer

      Every plugin ships a README covering commands, permissions, config keys and the API, including the warnings — where a setting is destructive, where a name is inconsistent. Two of them were rewritten from scratch because the old ones described features that did not exist. You are not buying a black box.

      Need something built?

      Custom plugin work, any of the above adapted to your server, or a look at why your existing setup is running badly. Tell me what your server does that the marketplace plugins cannot — or where it is losing ticks — and I will tell you honestly whether it is worth doing.
